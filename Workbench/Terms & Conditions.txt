SAFFRON EDGE Workbench Terms & Conditions Module Developer Implementation Brief Purpose Implement a policy-management and user-acknowledgement module inside the existing Saffron Edge Workbench. Users must be able to read current Terms & Conditions, review material changes, and retrieve prior versions. Authorized administrators must be able to draft, review, publish, version, and audit policy updates without hardcoding policy text into the frontend. Important safeguard: Do not use policy acceptance to confiscate, freeze, or arbitrarily restrict user funds. Do not require additional deposits, top-ups, fees, or credit-score payments to release an existing balance or process a withdrawal. Any restriction must have a valid, disclosed legal or contractual basis, documented reasons, and a support or dispute process. 1. User-facing Workbench experience Terms & Conditions navigation Add a persistent Terms & Conditions item in the Workbench navigation, accessible on desktop and mobile. Policy overview Show policy title, version, publication/effective date, last-updated date, and a clear link to the full document. Readable sections Use clearly labelled expandable sections: Withdrawals; Funds and Account Balances; Account Security and Confidentiality; Standard Properties Orders; Premium Properties Orders; Account Top-Ups; Properties Promotion System; Invitation and Referral Program; Operating Hours; and Credit Score System. First-time acknowledgement If a user has not acknowledged the applicable version, show a review screen before features legitimately subject to that policy. Do not block access to account records, support, or withdrawal initiation solely because the user declines a new version. Explicit acceptance Require an initially unticked checkbox and a separate I Agree action. Merely opening or scrolling through the document is not acceptance. Return access Let users reopen the current policy and retrieve previous versions they acknowledged. Provide print/download where practical. Change notice For material updates, explain what changed, when it takes effect, and whether renewed acknowledgement is requested. Do not retroactively change completed transactions. 2. Admin Policy Management Create an authenticated admin page called Policy Management with these capabilities: Capability Required behaviour Create policy Edit draft Create a new policy document and organize it into numbered sections. Edit unpublished content without changing the currently published policy. Preview Preview the policy as users will see it on desktop and mobile. Suggested database structure policies Suggested fields: id (primary key), title, version, status (draft/review/published/archived), content or structured section records, content_hash, created_by, approved_by, created_at, published_at, effective_at, and archived_at. Published versions must be immutable. policy_acceptances Suggested fields: id, user_id, policy_id/version, accepted_at, IP address where lawful and disclosed, user-agent where appropriate, content_hash, and acknowledgement method. Prevent duplicate or misleading acceptance records with suitable database constraints. policy_audit_logs Suggested fields: id, admin_user_id, action, policy_id, old_version, new_version, timestamp, reason/change summary, and request metadata. Restrict ordinary admin ability to edit or delete these logs. 4. Backend API requirements Example endpoint Purpose / access GET /api/policies/current Authenticated user: retrieve current published policy and version. GET /api/policies/{version} Authenticated user: retrieve a specific published historical version. POST /api/policies/{version}/accept Authenticated user: record explicit acknowledgement; derive user identity from server session. GET /api/me/policy-status Authenticated user: determine whether acknowledgement is current. POST /api/admin/policies Admin only: create a draft policy. PUT /api/admin/policies/{id} Admin only: update a draft; reject edits to published versions. POST /api/admin/policies/{id}/publish Authorized publisher: validate and publish an immutable version. GET /api/admin/policy-acceptances Authorized admin: search/export acknowledgement records. GET /api/admin/policy-audit-logs Authorized admin/auditor: inspect policy change history. 5. Acceptance and versioning workflow 1. User signs in. The backend checks whether the user acknowledged the currently applicable policy version. 2. If acknowledgement is required, display the complete policy and a concise change summary where applicable. 3. User actively ticks an unchecked acknowledgement box and selects I Agree. 4. Backend validates the authenticated session, policy status, version, and content hash, then records acceptance with a server-generated timestamp. 5. Workbench displays the accepted version and date in the user's policy history.6. When a material new version is published, notify affected users and request renewed acknowledgement where legally appropriate. 6. Security, privacy, and integrity • Enforce role-based access control. Ordinary users must not access admin policy endpoints. • Never trust user_id, timestamp, policy version, or acceptance status sent by the browser. Derive identity from the authenticated server session and generate timestamps server-side. • Use HTTPS, CSRF protection where applicable, input validation, output encoding, rate limiting, and secure session handling. • Store a cryptographic content hash for each published policy and acceptance record so the exact accepted document can be verified. • Log administrator actions and protect audit logs with restricted permissions and backups. • Collect IP address and device metadata only where lawful, necessary, disclosed in the privacy notice, and retained for a defined period. • Never expose one user's acceptance records or account information to another user. 7. UX and accessibility • Responsive layout for desktop, tablet, and mobile. • Readable typography, clear section numbering, accessible contrast, keyboard navigation, and screen-reader labels. • Do not hide important financial conditions only inside collapsed sections; provide a clear summary and direct links to full clauses. • Show policy version, effective date, and last-updated date consistently. • Provide visible confirmation after acceptance and a way to retrieve the accepted version. 8. Acceptance criteria / QA checklist Users can open and read the current policy on desktop and mobile. Users who have not acknowledged a required version see the acknowledgement flow. The checkbox is not preselected; acceptance requires an explicit action. The server stores the correct user, policy version, content hash, and server timestamp. Refreshing or signing in again does not lose or fabricate acceptance status. Published policy content cannot be silently edited; a new version is created instead. Authorized admins can preview, publish, and inspect version history. Acceptance reports are searchable and access-controlled. Material updates trigger the configured notification and acknowledgement process. Users retain access to support, transaction records, and withdrawal-request channels if they decline updated terms. No feature requires an extra deposit or payment merely to unlock, release, or withdraw an existing balance. 9. Implementation and deployment notes First inspect the existing codebase, framework, authentication flow, database, admin roles, and Workbench navigation. Reuse the existing design system and infrastructure where practical. Do not replace or migrate the production stack solely to add this module. Implement in staging, back up the database, test with test accounts, and obtain approval before production deployment. Expected deliverables: responsive user policy page; first-time/material-update acknowledgement flow; admin policy editor and publishing workflow; immutable version history; acceptance report; audit log; API/database migrations; automated tests; deployment and rollback notes.
